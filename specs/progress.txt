## Codebase Patterns

### Tamagui Token System

- Use `createTokens()` from `tamagui` package to add custom color tokens to Tamagui config
- Custom colors should use semantic naming with standard scale increments (50-950)
- The `defaultConfig.tokens` from v4 includes `radius`, `zIndex`, `space`, and `size` but NOT `color`
- Import `createTokens` from `tamagui`, not from `@tamagui/config/v4`
- Spacing tokens use 4px base unit (1 = 4px) for consistent layout rhythm
- Typography tokens follow modular scale ratio of 1.25 (major third) starting from 16px base
- Line height tokens provide optimal readability for different text sizes
- Size tokens should match spacing tokens for consistency across components

### Tamagui Theme System

- Define separate `light` and `dark` theme objects with semantic color mappings
- Map semantic names (background, color, primary, etc.) to token values using `tokens.color.tokenName`
- Theme colors are organized into categories: backgrounds, text, borders, shadows, interactive, feedback
- Light theme uses light backgrounds with dark text; dark theme uses dark backgrounds with light text
- Include interactive state variants: base, hover, press, and focus for each color
- Tamagui transforms token references into Variable objects with `val`, `key`, `name`, `variable` properties
- Access actual color values in tests via `theme.colorName.val`

### Tamagui Animation System

- Tamagui v4 uses CSS-based animation strings: `"cubic-bezier(x1, y1, x2, y2) duration"` format
- Extend `defaultConfig.animations` by spreading it and overriding the nested `animations` property
- There is NO `createAnimations()` function - use plain object with CSS animation strings
- Access animations via `config.animations.animations` (nested structure)
- Keep standard animations under 400ms for responsive feel; use 500ms+ for celebration animations
- Use consistent easing: `cubic-bezier(0.4, 0.0, 0.2, 1)` for standard, bouncy curve for celebrations

### Tamagui Styled Components

- Use `styled(YStack, { ... })` to create reusable UI component primitives
- Some style properties (like `borderRadius`) must be in variants, not base config due to TypeScript constraints
- Styled components are objects, not functions, but work with React.createElement()
- Define interactive states at same level as base styles: `hoverStyle`, `pressStyle`, `focusStyle`
- Use variants pattern for conditional styling: `variants: { prop: { value: { styles } } }` + `defaultVariants`
- Testing styled components requires matchMedia mock in test/setup.ts for Tamagui's media query support

### Tamagui Component Props

- Use `width` and `height` for sizing (not shorthands `w`/`h`) on YStack/XStack components
- Properties like `borderRadius` cannot be used inline on YStack/XStack - must be in styled component variants
- Use `flex` property (not shorthand `f`) for flex layout properties
- Tamagui v4 has `onlyAllowShorthands: true` which restricts available inline properties
- When creating function components that wrap Tamagui primitives, avoid dynamic style props that TypeScript rejects
- Text-based styled components (like Button) don't support: `textAlign`, `lineHeight`, `borderRadius` (use variants), `userSelect`
- Use `aria-label` and `role` for accessibility instead of deprecated `accessibilityLabel` and `accessibilityHint`

### TypeScript Type Definitions

- Group related interfaces in a single file (e.g., dashboard.ts for all dashboard types)
- Use enum for discriminated union types with snake_case string values for API compatibility
- Use `Date` type for timestamps (serialized to/from ISO strings in API calls)
- Use `Record<string, unknown>` for flexible metadata objects
- Nest related data in structured objects rather than flat properties
- Use JSDoc comments to document interface purpose

### TypeScript Import Best Practices

- Use `import type` for type-only imports to satisfy ESLint rule `@typescript-eslint/consistent-type-imports`
- Separate value imports (enums, functions) from type imports
- Remove trivially inferred type annotations (rule: `@typescript-eslint/no-inferrable-types`)
- Let TypeScript infer parameter types from default values (e.g., `greeting = 'Good morning'`)

### Mock Data Services

- Export both synchronous and asynchronous versions for flexibility
- Define mock data as module-level constants for consistency
- Async functions should accept delay parameter (default 500ms) to simulate network latency
- Mock data should include all enum variants for comprehensive testing
- Use JSDoc comments with `@example` tags to document usage patterns
