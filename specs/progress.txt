## Codebase Patterns

- Pattern: EAS Build configuration uses three profiles: development (with simulator support), preview (internal distribution), and production (store-ready builds)
- Pattern: iOS and Android use consistent bundle identifier: `com.languageden.app`
- Pattern: app.json must include expo-router plugin and enable typed routes experiment
- Pattern: EAS CLI is available via npx, no need to install as dependency
- Pattern: Use .npmrc with `engine-strict=true` and `node-linker=hoisted` for pnpm configuration
- Pattern: All npm scripts in package.json should be organized by category (dev, testing, quality, builds)
- Pattern: Always run format before committing to ensure code consistency
- Pattern: Use `React.JSX.Element` instead of `JSX.Element` for component return types to avoid ESLint deprecation warnings
- Pattern: Use `npx pnpm add` to install dependencies when pnpm is configured (not `npx expo install`)
- Pattern: Tamagui configuration uses `defaultConfig` from `@tamagui/config/v4` (not `config`)
- Pattern: TamaguiProvider wraps the root layout to provide theme and tokens globally
- Pattern: Add eslint-disable comment for no-empty-object-type on TamaguiCustomConfig interface
- Pattern: Tamagui v4 has `onlyAllowShorthands: true` - use `items`, `justify`, `bg` instead of full prop names
- Pattern: Tamagui components (YStack, H1) should be used instead of React Native primitives for cross-platform consistency
- Pattern: Expo web builds use Metro bundler when `"bundler": "metro"` is set in app.json web config
- Pattern: Create metro.config.js at project root using getDefaultConfig from expo/metro-config
- Pattern: Web builds output static SPA to dist/ folder, deployable to any static hosting
- Pattern: Supabase environment variables must be prefixed with `EXPO_PUBLIC_` for client-side access
- Pattern: Use .env.example (committed) as template and .env (gitignored) for actual credentials
- Pattern: .env files should include comments explaining where to get credentials
- Pattern: Supabase client is initialized in src/services/supabase.ts and exported as a singleton
- Pattern: Use bracket notation for environment variable access: `process.env['VARIABLE_NAME']` (TypeScript strict mode requirement)
- Pattern: Validate environment variables exist before initializing Supabase client with descriptive error messages
- Pattern: Vitest configuration uses node environment for pure TypeScript tests (domain layer)
- Pattern: Test files are placed next to the code they test with .test.ts or .test.tsx extension
- Pattern: Import test utilities explicitly from vitest: `import { describe, it, expect } from 'vitest'`
- Pattern: Domain layer tests should be pure TypeScript with no React or external dependencies
- Pattern: Configure path aliases in vitest.config.ts to match tsconfig.json paths
- Pattern: Use test/setup.ts for global test configuration (runs before each test file)
- Pattern: React component tests require jsdom environment - set in vitest.config.ts or use @vitest-environment comment
- Pattern: Install jsdom and react-test-renderer (matching React version) for component testing
- Pattern: Use server.deps.inline in vitest.config.ts to force transformation of problematic node_modules
- Pattern: Simple React components can be tested with React.createElement without full Testing Library setup
- Pattern: Supabase Auth configuration includes autoRefreshToken, persistSession, and custom storage adapter
- Pattern: Use expo-secure-store for encrypted token storage on native platforms, localStorage on web
- Pattern: Auth storage adapter detects platform with Platform.OS and provides async getItem/setItem/removeItem interface
- Pattern: Auth helper functions return Promise<{success, error?}> instead of throwing exceptions
- Pattern: Use `import type` for Supabase types (Session, User) to avoid ESLint consistent-type-imports errors
- Pattern: Modules using React Native Platform API may not be unit-testable in Vitest due to Flow syntax parsing issues
- Pattern: Supabase Edge Functions live in supabase/functions/ directory with each function in its own subdirectory
- Pattern: Edge Functions use Deno runtime - import from https URLs (e.g., 'https://deno.land/std@0.168.0/http/server.ts')
- Pattern: Exclude supabase/ directory from TypeScript compilation (tsconfig.json exclude array) and ESLint (eslint.config.mjs ignores array)
- Pattern: Edge Functions cannot be tested with Vitest (Deno runtime vs Node.js) - test via HTTP invocation after deployment
- Pattern: GitHub Actions CI workflow lives in .github/workflows/test.yml and runs on push/PR to main/master branches
- Pattern: CI installs pnpm with exact version from package.json using pnpm/action-setup@v4
- Pattern: All quality gates must pass in CI: type-check, lint, format:check, test (in that order)
- Pattern: Use --frozen-lockfile with pnpm install in CI to ensure reproducible builds
- Pattern: Test against multiple Node.js versions (18.x, 20.x) using matrix strategy for compatibility
